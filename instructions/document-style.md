# Document Style Rules

- Plain English. Short sentences. No buzzwords.
- Every section starts with one sentence saying what the section is for.
- Use tables for: scope, component changes, error handling, security decisions, test cases, assumptions, open items.
- Code blocks only for API examples and filename formats, always with fake values.
- One idea per paragraph.
- The reader may be a developer, QA, PO, or architect. Never assume they know the feature history.
- Backward compatibility gets its own section in every document. Always state clearly what does NOT change.
- Every open question lives in the Open Items table with an owner. No open questions hidden inside paragraphs.
